
What it is
An AI-powered farm management system for a multi-block almond farm. It continuously ingests sensor data, weather feeds, and manual field inputs, maintains a live state per block, and uses an AI reasoning engine to generate prioritised agronomic recommendations that the farm manager can accept, edit, or skip.

Architecture
Four layers working in a continuous loop: data ingestion → block state store → AI reasoning engine → recommendations and action log. The feedback loop closes when the manager logs what was actually done, writing back into the block state to inform future recommendations.

Data sources
The system ingests from four source types: in-field sensors (soil moisture, EC, temperature, humidity, wind, rainfall) updating every 15 minutes; weather forecast APIs updating every 3 hours; manual logs entered by the farm manager per event or weekly (irrigation runs, fertigation, spray applications, scouting observations, tissue samples), also initial data about the blocks (tree age, rootstock, soil and water test results to be uploaded in pdf format, and the system will extract the data from the pdf and store it in the database); and computed fields derived from the above (ETo, water deficit, GDD, chill hours, risk indices).

Interface — 8 pages
Login — email + password with remember me, there will be multiple users permissions for different modules within the applications, such as admin, worker who can only log activities, supervisor who can change different activities and add new activities, etc. After login, users with access to multiple farms will see a farm selector screen before reaching the dashboard; switching farms is available at any time from the top navigation bar without re-authenticating. Sign-in with Google is also offered, and always shows Google's account chooser so a person with more than one Google account picks which to use.
Dashboard — command center with four top metrics, 7-day weather strip, active alerts panel, block status grid (green/amber/red health status per block), upcoming calendar widget, and recent activity feed
Blocks — i want to upload an actual map of the farm, divide into physical blocks, each with the type and variety of tree/crop so the user can have a visual understanding on where he's working and on which tree per-block live profile across all five agronomic domains (soil & water, phenology, nutrition, pest & disease, weather) with inline alerts and source attribution. when creating the blocks, admin will feed the type of tree, date of planting and other relevant information ONCE to keep track of progress. Phenology is anchored by manual observations (bud break, full bloom) logged per block per season; harvest-window and stage predictions are projected from those anchors using accumulated growing degree days. Each block shows whether the knowledge base holds guides for its crop and variety, and a supervisor or admin can request them from there when it does not.
Calendar — month/week/day toggle, colour-coded events by activity type, ability to add events and log completions directly from entries. Calendar will include irrigation times, hours of run, litre/tree (for example from June to October you might run irrigation for 4 hours x 2 litres/ tree every 2 weeks) Fertigation times, type of fertilizer based on tree growth stage, amount of fertilizer. Spraying times, type of pesticide based on pest and disease pressure, amount of pesticide. Pruning, type of pruning based on tree growth stage after harvest (November to February)
Recommendations — AI-generated action cards filterable by category (irrigate, fertilize, spray, scout), each showing the action, rationale, and confidence score, with accept / edit / skip controls. Recommendations are grounded in a crop-aware knowledge base (retrieval-augmented generation over agronomy references such as the UC ANR almond production manual) and cite the sources they used. The search for references is variety-aware: a document about other varieties only (another cultivar's datasheet) is never given to a block, and the block's own variety is preferred. A card with no citation says 'Not source-backed' and why: no guides are loaded for the crop, no loaded guide covered the advice, or the knowledge base could not be read.
Activity log — searchable and filterable history of all actions taken across all blocks
Inventory — asset tracking with maintenance log history, and consumables tracking with usage logs linked to calendar events, searchable suggestions and low-stock alerts. Every stock change records who made it and when.
Settings — block configuration, sensor connections, weather API, irrigation controller (future integration), notification preferences, team/user management, and a language selector (English / Arabic / Turkish). Block configuration includes a knowledge base coverage view: for each crop and variety grown on the farm, the guides loaded for it and whether crop engine data exists, with a 'Request guides' control on every gap.

Navigation — top nav bar and a left sidebar, fully responsive for desktop and mobile field use. The sidebar must always fit inside the window: on a short or zoomed-in screen its links scroll between a pinned logo and a pinned user row, and the page itself never slides out of view.

Multi-farm support
A single login can own or be granted access to multiple farms. Each farm is a fully independent instance of the portal (its own blocks, calendar, inventory, recommendations, activity log, and settings). Permissions (admin/supervisor/worker) are scoped per farm, so a user can be admin on one farm and worker on another. All data, sensor feeds, and AI recommendations are isolated per farm with no cross-farm data leakage.

B2B multi-farm subscription (Phases 1–2 implemented; parts of Phase 3 and the owner-facing billing UI outstanding)
To support B2B clients (e.g. agricultural groups or consultants managing many farms), the system will introduce an organisation layer above farms. An organisation is the billing entity: it holds a Stripe customer and subscription, and all farms created under it are billed at a per-farm seat rate (quantity-based Stripe subscription). Key design decisions: (1) Organisation table — id, name, slug, billing_email, stripe_customer_id, stripe_subscription_id, subscription_status, farm_seats, created_by. (2) Organisation members table — maps users to orgs with roles: owner (billing access), admin (farm management), member. (3) Farms gain an organization_id FK. (4) Farm creation is gated: org must have an active or trialing subscription and the current farm count must be below farm_seats; creating a new farm beyond the current seat count triggers a Stripe quantity upgrade (prorated). (5) A Stripe webhook handler syncs subscription_status and farm_seats on checkout, upgrade, payment failure, and cancellation. (6) Past-due orgs get a banner and a grace period before farms go read-only; cancelled orgs do not lose data. (7) The first farm is free for 14 days (trialing) to reduce onboarding friction. (8) A Billing page in Settings lets the org owner open the Stripe Customer Portal to manage payment method, view invoices, and upgrade/downgrade seats. Rollout is phased: Phase 1 adds the organisation data model and replaces the hardcoded farm limit (built); Phase 2 adds Stripe checkout and webhooks (built); Phase 3 adds org-level team management and a cross-farm dashboard (the platform-level cross-farm overview is built; org-level team management is not). Still outstanding: the Billing page in Settings (item 8) that lets an org owner subscribe and open the Customer Portal, and enforcement of the past-due grace period (item 6).

Platform administration
A global super_admin role, granted manually and never self-service, gives platform operators an /admin area, reached by signing in normally and opening /admin (the app does not link to it). It holds: (1) a cross-farm overview listing every farm with a health level (stalled, needs attention, not set up, healthy), its main issue, last activity, open alerts, pending recommendations, block and member counts, owner and plan, with the farms that need a look first; (2) a read-only health page per farm for operations and support, showing the issues in plain words, when each scheduled job last produced data, which blocks are missing soil values, variety or planting date, each sensor as reporting, silent or never reported, what became of the last 30 days of recommendations (accepted, skipped with reason, expired, still open, and how many had no source), the farm's knowledge gaps, and its members with last sign-in; (3) a knowledge requests queue (see Knowledge base); (4) a subscribers list and per-organisation detail with members, farms and Stripe payment history. The platform operator is not a member of any farm: these pages show counts, times and settings only, never a farm's own log entries, notes, alert messages or recommendation text, and they change nothing on a farm. The same rule covers field assistant conversations, with one exception: a conversation a user has chosen to share with support (see Field assistant).

Knowledge base
The AI's advice is grounded in a library of agronomy documents (government guides, university extension material, peer-reviewed papers, breeder datasheets). Every document records where it comes from: publisher, country and region, language, authority type, whether it is regulatory, climate context, and the crop and varieties it applies to, so a recommendation can say when it rests on a source from another country or climate. The library is organised per crop and the system is multi-crop: a crop or variety with no documents is still fully usable, its recommendations are simply marked as not source-backed, and it never borrows another crop's or another variety's material. Crop names in English (singular or plural), Turkish and Spanish lead to the same documents. Documents are added by the platform operator only, after review; the system does not search for or download guides on its own, because a cited source must be trusted, legally usable and correctly described. Where guides are missing the farm sees it (in Settings, on the block and on each recommendation) and a supervisor or admin can send a tracked request with an optional note and link; there is one request per farm for each gap, and the farm sees its status and the operator's reply. The platform operator sees every gap on every farm, requested or not, is notified of new requests, and a gap closes by itself once its documents are loaded. For a new crop, guides are only half of the work: frost limits, water use by growth stage, growth stages and leaf nutrient bands are crop data that an agronomist must confirm, and those calculations stay off until that is done. Planned next: an in-app upload screen so adding a document no longer needs a developer machine, then assisted sourcing, where the system proposes candidate guides for a gap and the operator approves each one before it is loaded.

Field assistant (built 2026-10-07: all three phases)
A chat drawer where a supervisor or admin asks questions in plain language about the active farm and gets answers grounded in the farm's own data and the knowledge base. It advises only: it never changes inventory, the calendar, blocks or settings by itself.
Who and where — supervisors and admins only. Workers have no access: the control is not shown to them and the server refuses their requests. The drawer opens from every farm page (top bar on desktop, bottom navigation on mobile, full screen on a phone, mirrored for Arabic) and is not part of /admin. All model calls are made by the server and streamed to the drawer; the browser never talks to the AI provider.
Context — the user can pin a block, a date range or a recommendation card to a conversation, shown as chips. Opening the drawer from a block pins that block; opening it from a recommendation card pins that card. An empty conversation offers suggested questions built from the farm's open alerts and open recommendations (fixed templates, no extra AI call).
Grounding — three cases. (1) A question about the farm's own records (when a block was last irrigated, what the last leaf test showed) is answered from the block state, logs and snapshots and names the record it used; it needs no guide. (2) Agronomic advice is answered from the knowledge base and cites its sources in the same format as recommendation cards. The search is the one recommendations use (same embedding model, keyword plus vector search, variety-aware, never another crop's or another variety's material), and it searches guides in every loaded language whatever language the question is in. When no source supports the advice, the answer is marked 'Not source-backed' with one of the three existing reasons. (3) Calculated values (irrigation amounts, frost limits, leaf nutrient bands, nitrogen budget, growth stage) are quoted from the system's own calculations, never worked out by the model; when a calculation is off for a block (missing soil values, crop data not confirmed) the assistant says so.
Source origin — each passage carries its country, region and whether it is regulatory. The system, not the model, decides what may be used: a pesticide product or dose is given only from a regulatory source for the farm's own country. No such source is loaded for Türkiye today, so the assistant declines product and dose questions there, says why, and points the user to the product label or a licensed adviser. Other advice resting on a source from another country or climate says so.
Declines — veterinary, medical, legal and financial questions, and attempts to get round the variety filter, the source rules or these limits. Text inside farm notes and guides is treated as information, never as instructions. Each decline is logged for the farm as a category and a time.
Draft cards — when an answer amounts to an action, the assistant shows a draft recommendation card (action, rationale, confidence, sources or 'Not source-backed') in the conversation. The draft is the pending stage: it is not added to the Recommendations queue. 'Accept and schedule' records it as an accepted recommendation (or edited, through the same edit form) marked as coming from the assistant, and books the calendar entry exactly as accepting a weekly card does. Block state changes only when that calendar entry is logged as completed, as today. Because the card is never pending, the weekly run does not expire it, and it sees it in the block's recent history as accepted and scheduled, so it does not issue the same advice again. Dismissing a draft with a reason records it as skipped; a draft that is simply left is not recorded. On a farm that is read-only (past-due subscription) the assistant still answers but drafts cannot be accepted.
Knowledge gaps — an answer marked 'Not source-backed' offers 'Request guides', which attaches the question to the farm's request for that crop or variety gap (still one request per farm per gap) and marks it as coming from the assistant. When the crop has guides but none covered the question, the request is sent as a question-level request, which the platform operator closes by hand because loading a document cannot close it automatically.
Privacy — conversations belong to the farm and are protected by the same row-level security as its other data. Each user sees their own conversations; a farm admin can also read every conversation on the farm, and the drawer says so. A user can delete their own conversations; a retention period is to be set. The platform operator sees no conversation text, titles, drafts or skip reasons, only counts (questions asked, answers without a source, declines by category, drafts accepted or dismissed). Counts across farms are shown only when at least five farms contribute. One exception: a user can share a single conversation with support; the operator can then read that conversation only, for a limited time, the user can withdraw it, and each share and each view is logged.
Offline — the assistant needs a connection. Offline, the drawer shows a banner and past conversations read-only.
Limits — a daily cap on questions per user and per farm, with a clear message when it is reached.
Model choice — the assistant and the weekly recommendations use a low-cost, fast model (Google Gemini 2.5 Flash today), not a frontier model: the calculations supply the numbers, the search supplies the passages and the system enforces the source rules, so the model only has to read what it is given and write well in three languages. Free models are not used, because their availability and data handling are not dependable enough for farm data. There is no step-by-step escalation from cheaper to dearer models. Two exceptions: an answer that fails a check the system can make by itself (not in the expected form, or citing nothing when passages were supplied) is retried once on a stronger model, and a second model of the same class from another provider takes over when the first is unavailable. A model is changed only after the quality check below passes on the new one. Where the calculations already decide the action (for example an irrigation amount), the card is built from a template with no model call.
Quality check — a fixed set of test questions (farm-record questions, sourced advice, unsourced advice, declines, and questions in Turkish and Arabic against English and Spanish guides) is run before release and after any change to the search or the instructions.
Rollout — Phase 1: questions and answers with citations, pinning and conversation history. Phase 2: draft cards and 'Request guides'. Phase 3: share with support and the operator's counts.

Decision engine (all five layers built 2026-10-09 and running daily in shadow: science core, twelve engines, arbitrator, narrator, hard safeguards; the interface and the learning loop planned; full specification v3.0 in docs/nut-job-cdss-spec.md)
A rebuild of how recommendations are produced, so that every recommendation is scientific, traceable and auditable, for any crop. Today the weekly run asks the AI model to write the recommendations from block data and guide passages. In the decision engine the model writes nothing but the explanation: the action, the amount and the timing come from published calculations and written rules. The platform is generic machinery (calculators, decision engines, an optimiser, logging and learning); everything specific to a crop arrives as a Crop Knowledge Pack. The farm manager or agronomist keeps the final say (accept, edit or skip). The specification file holds the formulas, rule tables, starting values, acceptance tests and references; this section is the summary and the list of what has to be settled before building. Version 3.0 replaces the almond-only version 2.0 added earlier the same day.
The golden rule — a number, threshold, pest name, variety name or growth stage in platform code is a defect. It belongs in a pack.
Five layers, each with one job — (1) Science core: generic calculators set up by the pack: reference evapotranspiration (FAO-56 Penman-Monteith), a daily root-zone water balance with a crop coefficient worked out per block from canopy cover and height, degree-days (single sine, single triangle or averaging, as each model declares), chill (Dynamic Model portions, Utah units or chill hours) and heat to bloom, the expected water status of an unstressed plant, disease infection values from leaf wetness and temperature, frost risk, salinity and leaching, and nutrient budgets. It recommends nothing. (2) Decision engines: twelve generic engines, each applying the pack's rule tables to the block's state and proposing actions in one standard format, with the rule that fired, the pack version, the inputs used, the source, the expected result, the cost and the loss the action is expected to avoid, in money. An action that costs more than the loss it avoids becomes 'monitor'. (3) Arbitrator: chooses which proposed actions run, and on which day over the next 7 days, across all blocks and crops together, within labour, water, equipment and legal limits. It never invents an action or changes an engine's numbers, never silently drops a mandatory action, and shows every deferred action with the reason. Long-window seasonal tasks fill spare capacity. Food safety, legal limits, certification and water quotas are limits, never traded against money. (4) Narrator (the AI model): explains the plan, points out conflicting signals, asks for missing observations and drafts task text, in the user's app language. It may not create or change any number, date or amount; an answer containing a number it was not given is rejected, and when the model fails the plan is still shown with rule text from the pack. (5) Hard safeguards: fixed protective rules in platform code that override everything above; their limits come from the pack, product labels, equipment specifications and the farm's legal registry. They are never tuned by the learning loop and cannot be switched off by a prompt; changing one needs a code release signed off by the agronomist.
Crop binding — each block is bound to one crop pack and one variety (or variety mix) from it, with planting year, spacing, irrigation system and soil profile. A farm can run several crops at once. When a pack has no content for an engine (no chill model for an annual crop), that engine is inactive for those blocks and says so; it does not fail. Changing a block's pack version is an explicit, logged action, and every recommendation records the pack version that produced it.
The twelve engines — continuous (evaluated daily): phenology and dormancy (the clock for all the others; an observed stage overrides a predicted one), irrigation (including deficit strategies), fertigation and nutrition (annual budget, split by growth phase, doses placed on irrigation events, corrected from leaf analysis), salinity and leaching, frost protection (watch, warning, critical over the next 72 hours), insect pests (one engine, any number of pest models), diseases (infection-value models, growth-stage spray programmes, and risks driven by water or nitrogen status). Seasonal (a dated plan from pack templates, adjusted by growth stage and weather): pollination, canopy and pruning, weeds and groundcover, yield forecast (every other engine's expected loss depends on it), harvest. Engines read each other's results only through the shared block state.
Data — three speeds. Fast (minutes to hourly): weather station including leaf wetness, soil moisture and salinity probes, flow meters, valve and pump states, fertigation injector readings. Medium (days to weekly): trap counts, plant water status readings, growth stage scouting, pest and disease scouting, fruit set and fruit counts; the pack decides which observations the forms ask for. Slow (seasonal to yearly): soil and water chemistry, leaf analysis, yield and quality per block, canopy cover and height. Every fast reading is checked before use (no data, stale, out of range, stuck, sudden jump), every manual entry records who entered it and when, and every calculated value carries the age of its oldest input.
Hard safeguards — irrigation: close a valve that has run past its maximum time or shows a burst; raise an alert for an open valve with no flow; never irrigate automatically from sensor data when too few probes in the block are trustworthy; a time-capped emergency irrigation only when several valid probes agree the block is below its emergency floor. Spray and worker safety: no spraying in high wind, in calm-dawn inversion conditions or with rain forecast inside the product's rainfast period; no spray whose pre-harvest interval runs past the planned harvest date; no labour in a block during its re-entry interval; no product past its maximum applications per season; no product not registered for that crop in the farm's country; no bee-toxic product while hives are present or during bloom. Fertigation: stop injecting when the inline salinity or pH leaves its band; never inject without water flowing, and flush afterwards; cap any single dose at the pack's maximum. Frost and harvest: frost-protection water comes before all other night-time water use; wind machines and heaters run only inside their safety limits; no harvest task while a pre-harvest or re-entry interval is active in the block. Label values are entered and approved by the agronomist in the product library; none are invented in code.
Crop Knowledge Packs — a downloadable, versioned bundle of plain files holding all the science for one crop: manifest (crop, version, authors, regions where it is valid, licence, signature), crop profile, varieties, growth stage scale and its mapping to the phases the engines use, water, nutrition, salinity, frost, pest models, disease models, seasonal templates, yield model, links between engines, every parameter with its starting value, unit, bounds, source and status (sourced, expert estimate, to be sourced), learning measures, an evidence register and its own test suite. Product brands, prices and label values are not in packs; they are local and live in the farm's product library and legal registry. A pack is checked on install and on update (signature, every parameter and citation resolves, units declared, phases exist, its tests pass), and an engine that depends on a 'to be sourced' value stays in shadow until the value is filled in. A new version installs beside the old one, shows what changed, and blocks move to it only when the agronomist accepts. A small regional overlay can override values for a region without copying the whole pack.
Almond reference pack (version 0.1) — the first pack and the template for later ones: Makako and Vairo; irrigation rules with deficit irrigation during kernel fill as a switch; nitrogen removal of about 68 kg N per 1,000 kg of kernels with a four-part seasonal split; leaf bands; salinity threshold 1.5 dS/m; frost critical temperatures by stage; navel orangeworm and peach twig borer models; Alternaria, red leaf blotch and hull rot; seasonal templates. It lists the values still to be sourced before each engine can go live: chill and heat requirements for both varieties, growth stage boundaries, young-tree nitrogen by age, micronutrient bands, maximum single dose, sodium, chloride and boron limits by rootstock, frost damage levels, regional pest models, the remaining disease models, the seasonal templates and the product library.
Recommendation log and shadow mode — an append-only record of every recommendation: what, which block, crop and variety, when, the engine, rule, pack and pack version, the exact inputs, their age and the calibrated values in force, the expected result, the manager's decision with a reason (disagree with the science, knew something the system did not, resource or practical constraint, data looked wrong, other), whether it ran live or in shadow, and the observed result once it arrives. Shadow or live is set per engine and pack. In shadow the engine recommends and logs while the manager decides independently and records what was done. A newly installed pack starts in shadow for every engine; each engine goes live separately after its shadow record is reviewed.
Learning loop — adjusts values, never rules, and stores them as farm-level overrides on top of the pack, per block and variety; the pack itself is never changed by learning. It covers root-zone depletion and available water, crop coefficient, the water status baseline, pest and disease timing offsets, variety chill and heat requirements, the frost damage estimate, nutrient removal and efficiency, yield priors and damage estimates. Every value stays inside the pack's bounds. A recalibrated set runs in shadow beside the live one and is promoted only when it does better on the logged history and the agronomist approves; any promotion can be undone in one step. Manager overrides feed review queues; they do not change values directly. Safeguards are excluded. Anonymised calibration summaries can be shared with pack authors, by choice.
Interface — farm setup: assign pack, variety, planting year, spacing, irrigation system, soil profile and equipment to each block, and a product library. A crop pack manager for the agronomist: catalogue, installed packs with their validation report, updates with a list of changes, and Inactive, Shadow or Live per engine with reasons. Recommendation cards gain a 'Why' panel (rule, inputs with their age, source, pack version, expected result), a required reason on skip and edit, a collapsed list of deferred actions, a Shadow or Live badge per engine, filters by crop, block and engine, and a pinned safeguard banner that stays until acknowledged. The dashboard shows per-block tiles chosen by the pack and a data-quality strip. Block profiles show crop, variety, pack version and calibrated values with history. The calendar shows the 7-day plan, the season plans, re-entry and pre-harvest blocks, predicted events and frost nights. Mobile field forms are generated from the pack: trap checks, plant water status, growth stage scouting with stage photos, pest and disease scouting, fruit counts, canopy measurements, post-frost damage, harvest records. An engine area for the agronomist shows rule tables read-only, pack and farm values with bounds and history, and promote, reject and rollback.
Phases — all engines are built from the start; what differs is which can go live, which depends on data and pack completeness. Phase 1, before the first season: the whole platform (science core, framework, all twelve engines, arbitrator, narrator, safeguards, log, shadow mode, pack loader and validator, the learning machinery, all interface changes) and almond pack 0.1; done when every acceptance test passes, the almond pack validates with its to-be-sourced list reported, and a 30-day replay of past weather gives a daily set across all engines that the agronomist finds plausible. Phase 2, first season: every almond engine in shadow, the agronomist fills in the missing values and the product library, and engines go live one at a time (expected order: irrigation, insect pests, frost, fertigation, disease, then the seasonal engines). Phase 3, after the first season: the learning loop starts on logged outcomes, and a second crop pack proves that no platform code has to change.
Decided (2026-10-09; the user asked for these two to be decided for them, and they override the specification where it says otherwise) — Language: the decision engine is written in TypeScript inside this application, as pure modules in engines/ with tests, not as a separate Python service. Reasons: the calculations the app already has are TypeScript and are called directly by the snapshot job, the field assistant and the recommendation run; one language means one deployment, one test run and no second service to keep alive on a VPS that was CPU-capped on 2026-10-07; and the methods the Python packages provide are published formulas that the specification already writes out or cites. The specification's acceptance tests apply unchanged, and its Python code is the reference: each method is checked against the figures the specification gives, and against values produced once by the named Python packages (pyet, pyfao56, chillR) and kept as test data. The arbitrator needs a solver in place of OR-Tools; which one is chosen when the arbitrator is built, and the plan it returns must meet the same requirements. Pack ownership: packs are platform-wide. The platform operator installs, validates and updates them after review, exactly as guide documents are loaded today, and a pack's test suite must pass before any farm can use it. A farm does not download or install packs: it binds each block to an installed pack and variety, and asks for a missing crop through the existing request path. What stays per farm: the calibrated values on top of the pack, Shadow or Live per engine, the product library, and the choice of when a block moves to a new pack version, which a farm admin accepts after seeing what changed. Regional overlays are also installed by the operator and chosen by the farm. Reasons: a pack holds thresholds that drive physical work, so it needs the same review as a cited source; one reviewed copy cannot drift between farms; and it matches the rule that a crop without loaded data gets 'no data loaded'.
Where the specification and this project differ (to settle before building; points 1 and 3 are decided above, the rest are open) — (1) Language, decided 2026-10-09: TypeScript. See 'Decided' below. (2) Packs and crop profiles: version 3.0 is multi-crop, which matches this project's rule. The project already has a smaller form of the same idea: a crop profile per crop in utils/crops.ts, with 'no data loaded' for a crop without one. A pack would replace or absorb the profile, and the almond numbers that sit in code today (crop coefficients, heat model, leaf bands, frost thresholds, the nitrogen schedule) would move into the almond pack. (3) Who owns a pack, decided 2026-10-09: the platform. See 'Decided' below. A pack is a different thing from the knowledge base of guide documents, and the two need distinct names in the interface. (4) The agronomist: the specification gives an agronomist approval rights (product library, pack updates, promotions, live switches). The farm roles are admin, supervisor and worker; there is no agronomist role. (5) What already exists: an irrigation engine (FAO-56 water balance with one crop coefficient per growth stage and the same 40% allowable depletion), Hargreaves evapotranspiration, growing degree days from a base temperature, estimated chill hours, soil-probe and weather-station checks, and frost, leaf-nutrition, nitrogen and tree-maturity engines. Coverage was checked on 2026-10-09 and the user's rule is: an existing engine is dropped where the new plan covers its work. Covered, to be retired once the replacement passes its tests and has run beside the old one: irrigation, evapotranspiration, degree days and growth stage, chill, frost, leaf nutrition, the nitrogen budget, the soil-probe quality check and the daily snapshot. Not covered by the specification, so kept or added to the plan: the weather-station check against modelled weather; the alert rules (one alert per event, raised and cleared by rule, the leaf-sample reminder, the stale-forecast alert); tree maturity as the fallback for a young block whose canopy has not been measured; and accepting a variety the pack does not list, with the crop's general values. Nothing is removed before its replacement exists, because the live app (daily snapshot, block pages, field assistant, weekly run) runs on these engines today. Some of their numbers disagree with the almond pack: the frost engine holds measured 10%, 50% and 90% damage temperatures for Vairo at full bloom from a 2025 IRTA study (10% at −3.46 °C) while the pack gives one older value (−2.7 °C) and lists the damage levels as to be sourced; the leaf nitrogen ceiling is 2.6% in the app and 2.7% in the pack; adequate potassium starts at 1.0% in the app and 1.4% in the pack; boron is judged on leaves in the app and on hulls in the pack; the nitrogen budget uses a fertiliser-applied figure with a three-part split and no credits, the pack uses removal per yield with a four-part split, credits and an efficiency factor. (6) Region: the pack says it is valid for Mediterranean climates, to be confirmed. The farms are in Aksaray, Central Anatolia, which is continental. The navel orangeworm and peach twig borer models and their thresholds are from California, and the regional pests are to be sourced from Spain; which pests matter in Aksaray is for the agronomist to confirm. (7) Inputs not available today: solar radiation, humidity and wind for Penman-Monteith, hourly temperatures for chill, leaf wetness for the disease models, inline salinity and pH for fertigation, flow meters, and an irrigation controller for the valve safeguards (still a future integration); no sensors are registered on any farm. (8) Young trees: the live blocks were planted in late 2025, so deficit irrigation, hull split rules, harvest and yield-based loss do not apply until the trees bear, and the young-tree nitrogen values are among those still to be sourced. (9) Money: expected loss needs a price per farm and a yield forecast per block; neither exists yet. (10) Skip reasons: the app has three today (already done, disagree, no resources); the specification has five different ones. (11) Product rules: no regulatory source for Türkiye is loaded and the ministry's product register has no download, so the product library has to be entered by hand. (12) Size: Phase 1 is now the whole platform, all twelve engines, the pack system, the learning machinery and every interface change before the first season. Version 2.0 started with two engines. An order of work inside Phase 1 is needed.
Built so far (2026-10-09) — the foundation, as code with tests and with no connection to the live application yet: the calculators of the science core; the rule-table reader; the pack format with its loader and its checks on install; the standard form of an engine and of a proposed action; and almond pack 0.1 as plain files with its own tests. A command checks a pack and prints its report: errors, test results, which engines may go live, the values still to be sourced, the content not yet written and the notes for the agronomist. Not built: the twelve engines themselves, the hard safeguards, the arbitrator, the narrator, the recommendation log, shadow mode, the learning loop, installing a pack into the database, and every interface change. The live engines are unchanged.
Built so far, second step (2026-10-09, not yet deployed) — a daily run in shadow of three engines beside the present daily snapshot: growth phase, irrigation and frost. It fetches hourly weather for each farm (temperature, humidity, wind, solar radiation, rain; modelled for the location, not measured), keeps a daily water balance per block, and records what each engine concluded and every recommendation in an append-only log with the rule, the pack version, the inputs and the confidence. Nothing from it appears on the Recommendations page, in the alerts or on the calendar. The operator installs a pack with one command and binds blocks to it with another; a block then carries its pack, version and variety. What it needs before it says anything useful about irrigation on the live farms: the three values that turn canopy cover and height into a crop coefficient (to be sourced), and for each block its canopy cover, canopy height and the fraction of the surface the drip system wets, which have no form yet. Frost is assessed only at bloom and fruit set. When an engine cannot decide it says so and names what is missing; it does not report 'hold'. Still to come inside this part of the plan: prediction of bloom from chill and heat, plant water status readings, the manager's decision and the observed result in the log, and the switch from shadow to live.
Built so far, third step (2026-10-09, not yet deployed) — three more engines in the same shadow run: yield forecast, salinity and leaching, and fertigation and nutrition. The yield forecast takes the manager's estimate for a block this season, or the farm's target for a mature block scaled by the pack's curve of yield by age, and with a price per farm gives the money value of the block's crop. Salinity reads the latest soil and water analyses, reports the expected relative yield and the leaching requirement, and sets the leaching fraction irrigation adds, inside the pack's upper bound. Fertigation builds a yearly budget per nutrient from the yield forecast, splits it by growth phase, proposes a dose only together with an irrigation and never above the pack's maximum single dose, reads leaf analyses against the pack's bands, and asks for the leaf sample in the sampling month. Doses are amounts of nutrient, not products. Points settled by this step (point 9, provisionally, until the settings screens exist): the price is one figure per farm with its currency; the yield of a block is the manager's own estimate for the season, and the farm's existing yield target stands for a mature block. What these engines wait for with almond pack 0.1: a curve of yield by tree age, the nitrogen a young tree needs for growth, the maximum single dose, and an upper bound for the leaching fraction. A block that already has fertigation entries this year gets no dose proposal, because an entry names a product and not what it contains; that needs the product library.
Built so far, fourth step (2026-10-09, not yet deployed) — the insect pest and disease engines and the spray safeguards, in the same shadow run. Insect pests: for each pest in the pack, the start date for counting (set by the pack's rule from trap checks, or entered directly), degree-days from that date, and then monitor, prepare or treat by the pack's rules. Diseases: risk from leaf wetness and temperature where a pack gives such a model; a preventive programme timed from a recorded event such as petal fall; and advice to the other engines when water or nitrogen status raises a risk. Spray safeguards: every treatment proposal lists the farm's products for that pest or disease and, for each, whether it may be used and on which of the next four days, by the eight rules (wind, calm inversion conditions, rain before the product is rainfast, pre-harvest interval, re-entry interval, maximum applications, registration, bees). Two tables hold what these need: field observations (trap checks, counts, hull split, hives) and a product library per farm; neither has a form yet. Points settled by this step: the product library (point 11) is entered by hand per farm by a farm admin and a product counts only once approved; a product with any label value missing is blocked by the rule that needs it. The pests in the almond pack (point 6) stay as the specification gives them, marked unconfirmed for the region; whether they apply in Aksaray remains the agronomist's call. What these wait for: trap checks and a product library to be entered; hourly leaf wetness for the Alternaria model (no source); a damage estimate and a treatment cost before the navel orangeworm spray rule can fire; a rule table for peach twig borer.
Built so far, fifth step (2026-10-09) — the four seasonal engines, so all twelve engines now run in the shadow run: pollination, canopy and pruning, weeds and groundcover, and harvest. They share one mechanism: the pack lists the tasks of the season for each engine, each tied to a growth phase, to a number of days before or after a recorded event or the planned harvest, or to months of the year; a task can apply only to trees of a certain age, wait for dry weather, or be a spray that passes through the spray safeguards. Each task is proposed once in a season, when it falls due. Pollination also gives the number of hives for a block and warns of a day with no weather for bees to fly; pruning asks for the canopy to be measured when it has not been; harvest says when a block is ready from the pack's maturity measure, holds the harvest until every pre-harvest and re-entry interval has passed, and starts the irrigation cut-off before the planned harvest. A changed pack is a new version: the almond pack is now 0.1.1 in the repository, while 0.1.0 stays as installed; the operator installs 0.1.1 and the farm's blocks are moved to it. What these wait for with the almond pack: the task lists themselves (none is written yet), the hive density, the weather limits for bee flight, the hull split share at which to shake, and the days before harvest at which irrigation stops.
Built so far, sixth step (2026-10-09) — the arbitrator, the narrator and the remaining safeguards, so all five layers now exist and run daily in shadow. The arbitrator takes every action the engines propose on a farm and makes one plan for the next seven days across all its blocks, within the farm's daily labour, daily water, sprayers and water allocation. A spray is placed only on a day one of its products passes the spray safeguards; nothing that needs people in a block is placed during its re-entry interval; on a frost night a farm that protects with water keeps that water for frost protection. A mandatory action that cannot fit is reported with what stops it and is never dropped; every action left out carries its reason. The narrator explains the plan; an answer from the AI model is rejected if it contains any number it was not given, asked for once more, and replaced by text written from the rules if that fails too; in the daily shadow run the model is not called unless asked, and the rule text is used. The safeguards for sensors, valves, fertiliser injection and frost equipment are written and tested but connected to nothing, because the application controls no hardware yet. Points settled by this step: the solver (open since the language decision) is an exact search written for this problem inside the application, with no outside package; it returns the best plan found and says so when it stopped early. The farm's limits (labour hours a day, water a day, number of sprayers, how frost is protected) are settings per farm, empty until set, and an empty limit does not restrict the plan. What is left: the interface (step 7) and the learning loop (step 8).
Decided with the first build (2026-10-09) — Values in almond pack 0.1 (point 5): the pack takes the specification's values, except frost at full bloom for Vairo, where it keeps the measured 10%, 50% and 90% damage temperatures the application already uses (10% at −3.46 °C). Every value that differs from the live application carries a note for the agronomist in the pack's report: the leaf nitrogen ceiling, adequate potassium, boron on hulls or leaves, the nitrogen budget method, the frost values for other varieties and for young fruit. Where the specification gives no value (the parameters that turn canopy cover and height into a crop coefficient, root depth by age, the temperatures of the heat model), none was invented; they are listed as to be sourced. Order of work (point 12): (1) foundation, done; (2) hourly weather, a pack and variety per block, the recommendation log, and the phenology, irrigation and frost engines running in shadow beside the present daily snapshot, built and waiting to be deployed; (3) yield forecast and a price per farm, fertigation, salinity, built and waiting to be deployed; (4) the product library, the spray safeguards, insect pests and diseases, built and waiting to be deployed, with the field forms generated from the pack moved to step 7 with the other screens; (5) the seasonal engines, built; (6) sensor and valve safeguards, the arbitrator and the narrator, built; (7) installing packs by the operator, the farm interface and the shadow or live switches; (8) the learning machinery, and retiring each old engine after its replacement has run beside it. The open points each step touches are settled when that step starts.

Notifications
The system sends transactional email (team invitations, threshold alerts) and web push notifications for alerts. Users choose which notifications they receive in Settings. Platform operators receive a web push notification when a farm requests knowledge-base guides. (Email delivery is not configured yet, so in-app status and push are the working channels.)

Localisation
The application must support three languages: English, Arabic, and Turkish. The active language is set per user in their profile settings and persists across sessions. Arabic requires full RTL (right-to-left) layout mirroring — navigation, cards, tables, modals, and form fields must all flip correctly. Number formatting, date formats, and calendar week-start day must adapt to locale conventions. All UI strings, labels, error messages, and system-generated content (alerts, recommendation text, activity summaries) must be translatable; AI-generated agronomic recommendations should be returned in the user's active language where the underlying model supports it.

Mobile optimisation
The application is a primary field tool and must be fully usable on a smartphone browser without a native app install. Requirements: touch-friendly tap targets (minimum 44 × 44 px), bottom navigation bar on small screens replacing the top nav, swipe gestures for switching between blocks and calendar views, offline-capable reads (service worker caches the last-loaded dashboard, block profiles, and today's calendar so the manager can view data in poor-connectivity fields), background sync for activity log entries made offline, and lazy-loading of images and chart data to keep initial load under 3 seconds on a 4G connection.
