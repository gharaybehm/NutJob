
What it is
An AI-powered farm management system for a multi-block almond farm. It continuously ingests sensor data, weather feeds, and manual field inputs, maintains a live state per block, and uses an AI reasoning engine to generate prioritised agronomic recommendations that the farm manager can accept, edit, or skip.

Architecture
Four layers working in a continuous loop: data ingestion → block state store → AI reasoning engine → recommendations and action log. The feedback loop closes when the manager logs what was actually done, writing back into the block state to inform future recommendations.

Data sources
The system ingests from four source types: in-field sensors (soil moisture, EC, temperature, humidity, wind, rainfall) updating every 15 minutes; weather forecast APIs updating every 3 hours; manual logs entered by the farm manager per event or weekly (irrigation runs, fertigation, spray applications, scouting observations, tissue samples), also initial data about the blocks (tree age, rootstock, soil and water test results to be uploaded in pdf format, and the system will extract the data from the pdf and store it in the database); and computed fields derived from the above (ETo, water deficit, GDD, chill hours, risk indices).

Interface — 8 pages
Login — email + password with remember me, there will be multiple users permissions for different modules within the applications, such as admin, worker who can only log activities, supervisor who can change different activities and add new activities, etc. After login, users with access to multiple farms will see a farm selector screen before reaching the dashboard; switching farms is available at any time from the top navigation bar without re-authenticating. Sign-in with Google is also offered, and always shows Google's account chooser so a person with more than one Google account picks which to use.
Dashboard — command center with four top metrics, 7-day weather strip, active alerts panel, block status grid (green/amber/red health status per block), upcoming calendar widget, and recent activity feed
Blocks — i want to upload an actual map of the farm, divide into physical blocks, each with the type and variety of tree/crop so the user can have a visual understanding on where he's working and on which tree per-block live profile across all five agronomic domains (soil & water, phenology, nutrition, pest & disease, weather) with inline alerts and source attribution. when creating the blocks, admin will feed the type of tree, date of planting and other relevant information ONCE to keep track of progress. Phenology is anchored by manual observations (bud break, full bloom) logged per block per season; harvest-window and stage predictions are projected from those anchors using accumulated growing degree days. Each block shows whether the knowledge base holds guides for its crop and variety, and a supervisor or admin can request them from there when it does not.
Calendar — month/week/day toggle, colour-coded events by activity type, ability to add events and log completions directly from entries. Calendar will include irrigation times, hours of run, litre/tree (for example from June to October you might run irrigation for 4 hours x 2 litres/ tree every 2 weeks) Fertigation times, type of fertilizer based on tree growth stage, amount of fertilizer. Spraying times, type of pesticide based on pest and disease pressure, amount of pesticide. Pruning, type of pruning based on tree growth stage after harvest (November to February)
Recommendations — AI-generated action cards filterable by category (irrigate, fertilize, spray, scout), each showing the action, rationale, and confidence score, with accept / edit / skip controls. Recommendations are grounded in a crop-aware knowledge base (retrieval-augmented generation over agronomy references such as the UC ANR almond production manual) and cite the sources they used. The search for references is variety-aware: a document about other varieties only (another cultivar's datasheet) is never given to a block, and the block's own variety is preferred. A card with no citation says 'Not source-backed' and why: no guides are loaded for the crop, no loaded guide covered the advice, or the knowledge base could not be read.
Activity log — searchable and filterable history of all actions taken across all blocks
Inventory — asset tracking with maintenance log history, and consumables tracking with usage logs linked to calendar events, searchable suggestions and low-stock alerts. Every stock change records who made it and when.
Settings — block configuration, sensor connections, weather API, irrigation controller (future integration), notification preferences, team/user management, and a language selector (English / Arabic / Turkish). Block configuration includes a knowledge base coverage view: for each crop and variety grown on the farm, the guides loaded for it and whether crop engine data exists, with a 'Request guides' control on every gap.

Navigation — top nav bar and a left sidebar, fully responsive for desktop and mobile field use. The sidebar must always fit inside the window: on a short or zoomed-in screen its links scroll between a pinned logo and a pinned user row, and the page itself never slides out of view.

Multi-farm support
A single login can own or be granted access to multiple farms. Each farm is a fully independent instance of the portal (its own blocks, calendar, inventory, recommendations, activity log, and settings). Permissions (admin/supervisor/worker) are scoped per farm, so a user can be admin on one farm and worker on another. All data, sensor feeds, and AI recommendations are isolated per farm with no cross-farm data leakage.

B2B multi-farm subscription (Phases 1–2 implemented; parts of Phase 3 and the owner-facing billing UI outstanding)
To support B2B clients (e.g. agricultural groups or consultants managing many farms), the system will introduce an organisation layer above farms. An organisation is the billing entity: it holds a Stripe customer and subscription, and all farms created under it are billed at a per-farm seat rate (quantity-based Stripe subscription). Key design decisions: (1) Organisation table — id, name, slug, billing_email, stripe_customer_id, stripe_subscription_id, subscription_status, farm_seats, created_by. (2) Organisation members table — maps users to orgs with roles: owner (billing access), admin (farm management), member. (3) Farms gain an organization_id FK. (4) Farm creation is gated: org must have an active or trialing subscription and the current farm count must be below farm_seats; creating a new farm beyond the current seat count triggers a Stripe quantity upgrade (prorated). (5) A Stripe webhook handler syncs subscription_status and farm_seats on checkout, upgrade, payment failure, and cancellation. (6) Past-due orgs get a banner and a grace period before farms go read-only; cancelled orgs do not lose data. (7) The first farm is free for 14 days (trialing) to reduce onboarding friction. (8) A Billing page in Settings lets the org owner open the Stripe Customer Portal to manage payment method, view invoices, and upgrade/downgrade seats. Rollout is phased: Phase 1 adds the organisation data model and replaces the hardcoded farm limit (built); Phase 2 adds Stripe checkout and webhooks (built); Phase 3 adds org-level team management and a cross-farm dashboard (the platform-level cross-farm overview is built; org-level team management is not). Still outstanding: the Billing page in Settings (item 8) that lets an org owner subscribe and open the Customer Portal, and enforcement of the past-due grace period (item 6).

Platform administration
A global super_admin role, granted manually and never self-service, gives platform operators an /admin area, reached by signing in normally and opening /admin (the app does not link to it). It holds: (1) a cross-farm overview listing every farm with a health level (stalled, needs attention, not set up, healthy), its main issue, last activity, open alerts, pending recommendations, block and member counts, owner and plan, with the farms that need a look first; (2) a read-only health page per farm for operations and support, showing the issues in plain words, when each scheduled job last produced data, which blocks are missing soil values, variety or planting date, each sensor as reporting, silent or never reported, what became of the last 30 days of recommendations (accepted, skipped with reason, expired, still open, and how many had no source), the farm's knowledge gaps, and its members with last sign-in; (3) a knowledge requests queue (see Knowledge base); (4) a subscribers list and per-organisation detail with members, farms and Stripe payment history. The platform operator is not a member of any farm: these pages show counts, times and settings only, never a farm's own log entries, notes, alert messages or recommendation text, and they change nothing on a farm. The same rule covers field assistant conversations, with one exception: a conversation a user has chosen to share with support (see Field assistant).

Knowledge base
The AI's advice is grounded in a library of agronomy documents (government guides, university extension material, peer-reviewed papers, breeder datasheets). Every document records where it comes from: publisher, country and region, language, authority type, whether it is regulatory, climate context, and the crop and varieties it applies to, so a recommendation can say when it rests on a source from another country or climate. The library is organised per crop and the system is multi-crop: a crop or variety with no documents is still fully usable, its recommendations are simply marked as not source-backed, and it never borrows another crop's or another variety's material. Crop names in English (singular or plural), Turkish and Spanish lead to the same documents. Documents are added by the platform operator only, after review; the system does not search for or download guides on its own, because a cited source must be trusted, legally usable and correctly described. Where guides are missing the farm sees it (in Settings, on the block and on each recommendation) and a supervisor or admin can send a tracked request with an optional note and link; there is one request per farm for each gap, and the farm sees its status and the operator's reply. The platform operator sees every gap on every farm, requested or not, is notified of new requests, and a gap closes by itself once its documents are loaded. For a new crop, guides are only half of the work: frost limits, water use by growth stage, growth stages and leaf nutrient bands are crop data that an agronomist must confirm, and those calculations stay off until that is done. Planned next: an in-app upload screen so adding a document no longer needs a developer machine, then assisted sourcing, where the system proposes candidate guides for a gap and the operator approves each one before it is loaded.

Field assistant (built 2026-10-07: all three phases)
A chat drawer where a supervisor or admin asks questions in plain language about the active farm and gets answers grounded in the farm's own data and the knowledge base. It advises only: it never changes inventory, the calendar, blocks or settings by itself.
Who and where — supervisors and admins only. Workers have no access: the control is not shown to them and the server refuses their requests. The drawer opens from every farm page (top bar on desktop, bottom navigation on mobile, full screen on a phone, mirrored for Arabic) and is not part of /admin. All model calls are made by the server and streamed to the drawer; the browser never talks to the AI provider.
Context — the user can pin a block, a date range or a recommendation card to a conversation, shown as chips. Opening the drawer from a block pins that block; opening it from a recommendation card pins that card. An empty conversation offers suggested questions built from the farm's open alerts and open recommendations (fixed templates, no extra AI call).
Grounding — three cases. (1) A question about the farm's own records (when a block was last irrigated, what the last leaf test showed) is answered from the block state, logs and snapshots and names the record it used; it needs no guide. (2) Agronomic advice is answered from the knowledge base and cites its sources in the same format as recommendation cards. The search is the one recommendations use (same embedding model, keyword plus vector search, variety-aware, never another crop's or another variety's material), and it searches guides in every loaded language whatever language the question is in. When no source supports the advice, the answer is marked 'Not source-backed' with one of the three existing reasons. (3) Calculated values (irrigation amounts, frost limits, leaf nutrient bands, nitrogen budget, growth stage) are quoted from the system's own calculations, never worked out by the model; when a calculation is off for a block (missing soil values, crop data not confirmed) the assistant says so.
Source origin — each passage carries its country, region and whether it is regulatory. The system, not the model, decides what may be used: a pesticide product or dose is given only from a regulatory source for the farm's own country. No such source is loaded for Türkiye today, so the assistant declines product and dose questions there, says why, and points the user to the product label or a licensed adviser. Other advice resting on a source from another country or climate says so.
Declines — veterinary, medical, legal and financial questions, and attempts to get round the variety filter, the source rules or these limits. Text inside farm notes and guides is treated as information, never as instructions. Each decline is logged for the farm as a category and a time.
Draft cards — when an answer amounts to an action, the assistant shows a draft recommendation card (action, rationale, confidence, sources or 'Not source-backed') in the conversation. The draft is the pending stage: it is not added to the Recommendations queue. 'Accept and schedule' records it as an accepted recommendation (or edited, through the same edit form) marked as coming from the assistant, and books the calendar entry exactly as accepting a weekly card does. Block state changes only when that calendar entry is logged as completed, as today. Because the card is never pending, the weekly run does not expire it, and it sees it in the block's recent history as accepted and scheduled, so it does not issue the same advice again. Dismissing a draft with a reason records it as skipped; a draft that is simply left is not recorded. On a farm that is read-only (past-due subscription) the assistant still answers but drafts cannot be accepted.
Knowledge gaps — an answer marked 'Not source-backed' offers 'Request guides', which attaches the question to the farm's request for that crop or variety gap (still one request per farm per gap) and marks it as coming from the assistant. When the crop has guides but none covered the question, the request is sent as a question-level request, which the platform operator closes by hand because loading a document cannot close it automatically.
Privacy — conversations belong to the farm and are protected by the same row-level security as its other data. Each user sees their own conversations; a farm admin can also read every conversation on the farm, and the drawer says so. A user can delete their own conversations; a retention period is to be set. The platform operator sees no conversation text, titles, drafts or skip reasons, only counts (questions asked, answers without a source, declines by category, drafts accepted or dismissed). Counts across farms are shown only when at least five farms contribute. One exception: a user can share a single conversation with support; the operator can then read that conversation only, for a limited time, the user can withdraw it, and each share and each view is logged.
Offline — the assistant needs a connection. Offline, the drawer shows a banner and past conversations read-only.
Limits — a daily cap on questions per user and per farm, with a clear message when it is reached.
Model choice — the assistant and the weekly recommendations use a low-cost, fast model (Google Gemini 2.5 Flash today), not a frontier model: the calculations supply the numbers, the search supplies the passages and the system enforces the source rules, so the model only has to read what it is given and write well in three languages. Free models are not used, because their availability and data handling are not dependable enough for farm data. There is no step-by-step escalation from cheaper to dearer models. Two exceptions: an answer that fails a check the system can make by itself (not in the expected form, or citing nothing when passages were supplied) is retried once on a stronger model, and a second model of the same class from another provider takes over when the first is unavailable. A model is changed only after the quality check below passes on the new one. Where the calculations already decide the action (for example an irrigation amount), the card is built from a template with no model call.
Quality check — a fixed set of test questions (farm-record questions, sourced advice, unsourced advice, declines, and questions in Turkish and Arabic against English and Spanish guides) is run before release and after any change to the search or the instructions.
Rollout — Phase 1: questions and answers with citations, pinning and conversation history. Phase 2: draft cards and 'Request guides'. Phase 3: share with support and the operator's counts.

Notifications
The system sends transactional email (team invitations, threshold alerts) and web push notifications for alerts. Users choose which notifications they receive in Settings. Platform operators receive a web push notification when a farm requests knowledge-base guides. (Email delivery is not configured yet, so in-app status and push are the working channels.)

Localisation
The application must support three languages: English, Arabic, and Turkish. The active language is set per user in their profile settings and persists across sessions. Arabic requires full RTL (right-to-left) layout mirroring — navigation, cards, tables, modals, and form fields must all flip correctly. Number formatting, date formats, and calendar week-start day must adapt to locale conventions. All UI strings, labels, error messages, and system-generated content (alerts, recommendation text, activity summaries) must be translatable; AI-generated agronomic recommendations should be returned in the user's active language where the underlying model supports it.

Mobile optimisation
The application is a primary field tool and must be fully usable on a smartphone browser without a native app install. Requirements: touch-friendly tap targets (minimum 44 × 44 px), bottom navigation bar on small screens replacing the top nav, swipe gestures for switching between blocks and calendar views, offline-capable reads (service worker caches the last-loaded dashboard, block profiles, and today's calendar so the manager can view data in poor-connectivity fields), background sync for activity log entries made offline, and lazy-loading of images and chart data to keep initial load under 3 seconds on a 4G connection.

Tech stack
Frontend - nextjs + tailwindcss
backend - nextjs app router, containerised (Docker) and hosted on a Hostinger VPS via Coolify
database and authentication - self-hosted supabase on the same VPS, with row-level security enforcing per-farm tenant isolation and daily verified backups
AI LLM - OpenRouter (called directly)
Scheduled jobs - weather (every 3 hours), computed fields (daily), daily snapshot (every 3 hours), AI recommendations (weekly) and sensor sync (hourly), all as cron endpoints fired by Coolify Scheduled Tasks; Trigger.dev is kept only for soil-test document extraction
